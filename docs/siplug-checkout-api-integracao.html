Documentação prática de integração

Siplug Checkout API

Rotas, contratos de requisição, configuração e fluxo inicial para o backend central.

Gerado em 24/08/2026 a partir do código-fonte deste repositório.

ESCOPO
Este documento descreve apenas siplug-checkout-api. Os PDFs das demais APIs são referências externas e não substituem os contratos verificados aqui.

1. Visão geral

API NestJS de checkout, transações, gateways, clientes de pagamento, assinaturas, faturas e divisão de pagamentos. Valores monetários nos contratos principais são inteiros em centavos.

Base URL: http://{host}:{APP_PORT}/api/v1. No Docker local: http://localhost:8085/api/v1.

Autenticação: rotas que recebem token aceitam corpo ou Authorization: Bearer {token}. O backend central deve padronizar o cabeçalho e não registrar tokens.

Segurança: nunca documente ou encaminhe DATABASE_URL, CRYPT_KEY e providerToken. Use variáveis de ambiente/vault.

3. Fluxo inicial para o backend central

  1. Suba a API e o MySQL com docker compose up --build; valide GET /api/v1/health.
  2. Cadastre/sincronize gateway, credencial e cliente de pagamento.
  3. Crie uma sessão em POST /checkout-sessions/register; guarde seu identificador.
  4. Execute POST /payments/process com sessão, método e dados do pagamento; use uma idempotencyKey por tentativa lógica.
  5. Consulte ou sincronize a transação e configure os webhooks públicos do provedor.
  6. Quando aplicável, calcule/registre split. Para recorrência, cadastre plano, assinatura e processe faturas via agendador central.

Exemplo — criar sessão

POST /api/v1/checkout-sessions/register
Authorization: Bearer {token}
{ "officeId":"uuid", "clientId":"uuid", "gatewayId":"uuid", "paymentType":"one_time", "amount":1990, "currency":"BRL", "items":[{"name":"Plano mensal","quantity":1,"unitAmount":1990}] }

Exemplo — processar pagamento

POST /api/v1/payments/process
Authorization: Bearer {token}
{ "checkoutSessionId":"uuid", "paymentMethod":"card", "idempotencyKey":"pedido-123-1", "paymentData":{"token":"tokenizado-pelo-gateway"} }

4. Convenções

  • “Obrigatório” vem do request HTTP atual; campos opcionais podem aceitar null quando o tipo o declara.
  • Respostas de sucesso geralmente seguem { status: "success", message, data }; erros tratados retornam { status: "error", message } com HTTP 400.
  • metadata e config aceitam objeto livre; versione suas chaves no backend central.

6. Webhooks e retornos

O prefixo é /api/v1, exceto POST /w/p/:apiCredentialId, excluída explicitamente pelo bootstrap. Configure URLs públicas e valide assinatura/origem por gateway.

  • POST /api/v1/webhooks/stripe/:apiCredentialId
  • POST /api/v1/webhooks/gateways/pagseguro/:apiCredentialId e POST /w/p/:apiCredentialId
  • POST /api/v1/webhooks/gateways/mercado-pago[/ :apiCredentialId], PicPay, PayPal, InfinitePay e roteador /:gatewayProvider
  • GET /api/v1/paypal/checkout/return/:apiCredentialId e .../cancel/:apiCredentialId são callbacks de redirecionamento.

7. Observações de integração

Não há Swagger/OpenAPI configurado no bootstrap. Encapsule esta API num cliente do backend central, com timeout, propagação do cabeçalho de autenticação, idempotência e processamento idempotente de webhooks. Em homologação, valide valores aceitos por paymentMethod, paymentType, status e formato de paymentData, pois dependem do gateway/credencial.
